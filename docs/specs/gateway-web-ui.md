# Gateway web UI

## What it does
The gateway serves a web UI at `/` on its public address. A person signs in with an invitation-set password, and manages the templates, sandboxes, API keys, members and viewers of one tenant. The sandbox screen opens an interactive shell into a running sandbox, streams the tenant event log, publishes a port, sleeps the sandbox and destroys it. An operator also creates tenants and sets their caps. The UI replaces the bare sign-in and consent pages that `internal/gateway/pages.go` serves now.

## Decisions
- The UI is a React SPA in `web/`, built by Bun and Vite, embedded with `//go:embed dist/*` and served by `kiln-gateway` — one binary and one deploy, the way the gateway already ships.
- `web/dist` is not committed; `web/dist/.gitkeep` satisfies the embed glob, and the Dockerfile gains a Bun stage before the Go build — a committed bundle is a binary diff on every UI commit and it goes stale in silence.
- The stack copies `skael-dev/skael/web`: React 19, Vite, Tailwind v4, shadcn (new-york, neutral), TanStack Query, react-router — a known-good setup, and no second style to learn.
- The SPA calls `/v1` with a client generated by `@hey-api/openapi-ts` from the `openapi.json` that `internal/apispec` produces — the UI restates no route, and a route change breaks the build.
- The browser authenticates with the auth-all session cookie, and holds no key — a front-end credential that creates sandboxes must not exist.
- The gateway sets `WithCookieSameSite(http.SameSiteStrict)`, `WithStrictOriginCheck()` and `WithTrustedOrigins(BaseURL)` — the cookie authenticates writes, so a cross-site write must fail.
- `KILN_LOGIN_PATH` and `KILN_CONSENT_PATH` point at the SPA routes `/sign-in` and `/consent`, and `pages.go` is deleted — one sign-in screen, not two.
- The SPA index answers an unknown path, but never `/v1`, `/auth`, `/mcp`, `/healthz`, `/openapi.json`, `/llms.txt`, `/llms-full.txt` or `/.well-known/` — a client-side route must not shadow the API.
- The member role `viewer` is renamed `reader` in `cmd/kiln-gateway/main.go` — `viewer` names a preview login in this codebase, and one word means one thing.
- `editor` manages sandboxes, templates, API keys, members and viewers. `reader` sees the same lists and nothing else. `operator` adds a tenants screen and a tenant switcher — the roles already carry these permission statements.
- The UI asks the same permission strings the routes ask, and hides a control the caller may not use; the server still refuses — a hidden control is a convenience, not a check.
- There is no public sign-up. The operator creates a tenant, and a tenant's operator invites a person by email through the `organizations` invitation flow — a box that runs a stranger's code as root does not open itself to strangers.
- The plaintext of an API key appears once, at creation — the gateway stores a hash, so a second view is impossible.
- Viewers have their own screen, apart from members, and it states that a viewer opens published previews and reaches no sandbox, template or key — one list of two kinds of login teaches the wrong model.
- The host serves `GET /v1/sandboxes/{id}/terminal` as a WebSocket upgrade. Binary frames carry PTY bytes both ways, and a JSON frame carries `{"cols":n,"rows":n}` — every comparable product gives a shell in the browser.
- `kilninit` gains a `terminal` request kind. It opens `/dev/ptmx`, runs the shell as the session leader on the slave, and copies bytes to and from the vsock connection — `golang.org/x/sys` is already a dependency, so the PTY needs no new package.
- The gateway forwards the terminal through its existing `/v1` forwarder, with the same tenant header — `httputil.ReverseProxy` forwards an upgrade, and a second path would need a second authorization rule.
- `github.com/coder/websocket` joins `go.mod` — it is maintained, small and needs no C.
- The terminal needs `sandbox:exec`, so `reader` does not get one — a reader must not run code.
- `apispec` names the terminal operation with a `Terminal: true` flag. `checks/openapi.sh` requires the route and documents it as an upgrade, and the generated SDKs skip it — OpenAPI 3.1 cannot describe a WebSocket, and the handwritten SDK layer already covers streams.
- The event log is `GET /v1/events` over `EventSource`, filtered to the open sandbox, and it also drives live state in the sandbox and template lists — a build that finishes appears without a refresh.
- `just check` builds the SPA and fails on a TypeScript or lint error — an embedded bundle that does not compile ships a broken UI.

## Out
- No file browser. `readFile`, `writeFile` and the shell reach every file, and a directory listing needs a new host route.
- No public sign-up and no password reset by self-service. An invitation is the only route in.
- No billing, usage charts or metering screens.
- No mobile layout beyond what the component set gives.
- No Playwright suite. The UI is verified by driving it.
- No second API for the UI. The UI is a client of `/v1`.

## How I know it works
- `docker build .` produces an image, and `https://api.statapad.com/` serves the UI.
- An operator signs in, creates a tenant, sets its caps, and the tenant appears in `GET /operator/tenants`.
- The operator invites an address. The invitation link sets a password, and that person signs in as an `editor` of that tenant alone.
- The editor builds a template from `docker.io/library/python:3.12-slim`, and the list shows the build reaching ready without a page refresh.
- The editor creates a sandbox from that template, opens the terminal, runs `python -c "print(1+1)"`, and sees `2`. The window resize changes `stty size` inside the sandbox.
- The editor publishes port 8000, opens the hostname in a second tab, then retires the port and the hostname stops answering.
- The editor sleeps the sandbox, and the sandbox keeps its id and its hostnames. The editor wakes it, and the terminal opens again.
- The editor creates an API key, copies the plaintext once, reloads the page, and it is gone. `curl` with that key lists the same sandboxes.
- A `reader` of the same tenant sees the lists, and the terminal, the create buttons and the keys screen are absent. A direct `POST /v1/sandboxes` with that session returns 403.
- A `viewer` created on this screen opens a published preview of this tenant, and gets a login challenge on another tenant's preview.
- A cross-site form posted to `/v1/sandboxes` with the session cookie present is refused.
- A `GET /v1/sandboxes` from the browser with no session returns 401 and the SPA shows the sign-in screen.
- An MCP client starts the authorization code flow, and the SPA sign-in and consent screens complete it.
- `just check` passes, and it fails when a route exists in `apispec` and not in the generated client.
